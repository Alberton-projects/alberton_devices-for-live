# Review of the Max for Live devices — 2026-08-04

Read out of the device files, not out of Live. Ordered by what actually affects the
music. Devices covered: the ten written here; *Gated Delay* and *Live Scratcher* were
skipped as third-party (nothing jumped out of either).

> **Status: everything below is fixed except where marked NOT DONE.** Every file touched
> has its original beside it with a `.orig-2026-08-04` suffix; reverting is a rename.
> §1-8 were verified by reading, not by listening. §9-11 came later, from a session with
> the audio running and the owner playing — and that session overturned two conclusions
> reached from reading alone. Read §11 before trusting anything here about *sound*.

**One diagnosis in the first draft of this review was wrong** and is corrected in §2: the
Kit Selector does store the resample slider (an `autopattr @greedy 1` catches it, and
saved preset data already exists under the key `vocals_fx[1]`). The defect is narrower
than first written, and the fix first proposed — renaming the varname — would have
orphaned that saved data.

## 1. Bass Mapper returns the wrong note, 103 times out of 128 — FIXED

`alberton-bass-mapper.js`, `foldToBassRange`. Two copies, both active — *Bass Synth* and
*Bass Electric*.

The fold is done modulo the **width of the window in semitones**:

    var BASS_RANGE = BASS_HIGH - BASS_LOW + 1;      // 25
    var offset = (pitch - BASS_LOW) % BASS_RANGE;
    return BASS_LOW + offset;

25 is not a multiple of 12, so folding does not preserve the pitch class. Every note
outside 36–60 comes back as a *different note*, not the same note an octave down:

| you play | you get | you should get |
|---|---|---|
| C#3 (61) | C1 (36) | C#2 (49) |
| E3 (64) | D#1 (39) | E2 (52) |
| C4 (72) | B1 (47) | C3 (60) |
| C5 (84) | B2 (59) | C3 (60) |
| B0 (35) | C3 (60) | B1 (47) |

Only the 25 notes already inside the window survive intact. The device does not transpose
a bass line — it rewrites it.

Fix — fold by octaves instead:

    function foldToBassRange(pitch) {
        while (pitch > BASS_HIGH) pitch -= 12;
        while (pitch < BASS_LOW)  pitch += 12;
        return pitch;
    }

**Done.** Re-run against a stub of the Max globals: 0 of 128 notes now change name, and
every result lands inside 36-60. **Listen before you keep it** — two octaves is a narrow
window, and if bass parts have been written *against* the old behaviour they will now
sound different. `alberton-bass-mapper.js.orig-2026-08-04` puts it back.

## 2. Kit Selector never applies the recalled Resample FX — FIXED

`Alberton_Kit_Selector_V4.3.amxd`. Nine FX channels; eight of them come back correctly.

Every channel is a `multislider` whose **varname** matches the channel, plus a
`pattr @bindto <varname>` whose job on recall is to push the restored value on to
`live_controller.js`, which writes it to the actual rack. The resample slider was cloned
from the vocals one: Max auto-named it `vocals_fx[1]`, its *parameter* was renamed to
`resample_fx[1]`, and its **varname never was**. So `pattr @bindto resample_fx` bound to
a name that does not exist — 1 broken binding out of 10.

The value *was* being stored, by the `autopattr @greedy 1`, under the key `vocals_fx[1]`
(there is saved preset data under that key in the patcher already). What never happened
is the push: on recall the slider showed the right numbers while the rack kept its old
macro values.

**Done** — by pointing the pattr at the name that exists, `@bindto vocals_fx[1]`. The
alternative, renaming the slider to `resample_fx`, would have matched the naming scheme
but orphaned every value already saved under the old key.

## 3. Five devices depend on a .js file lying beside them — FIXED

Only the Step Sequencer embeds its script. These load theirs from the folder:

| Device | Script |
|---|---|
| Drum Mapper | `alberton-drum-mapper.js` |
| Bass Mapper | `alberton-bass-mapper.js` |
| Transpose Q | `alberton-transpose-v2.js` |
| Kit Selector V4.3 | `live_controller.js` |
| Gamepad v80 | `slot-fire.js` |

All five files were present, so everything worked here. But the `.amxd` alone was not
the device: copy one to another machine and the `js` object fails to instantiate and the
device does nothing, with no error a performer would notice.

**Done** — `embed_scripts.py` in this folder rewrites a device as a *collective*, the
same container form Max produces with *File → Show Dependencies → Consolidate*. The
builder was checked by rebuilding two Max-written collectives byte for byte before it was
used on anything.

**One consequence to know about.** Both copies of each script now exist: one inside the
device, one still in the folder. Which one Max prefers has not been tested. If you edit a
script and the change does not take, that is why — re-run `embed_scripts.py --write` on
the device after editing.

## 4. Both mappers can hang a note — FIXED

`alberton-drum-mapper.js` and `alberton-bass-mapper.js` — the same code shape in both,
copy-pasted.

Note-off is matched by remembering the mapping in `activeNotes[inputPitch]`. If the same
input pitch arrives twice before the first note-off — two sources into one track, a
sequencer retriggering a held note, a stuck controller — the second note-on overwrites
the entry, and the first note-off then releases the wrong note. The other one never gets
a note-off at all.

**Done** in both scripts: `activeNotes` now holds a *queue* of output pitches per input
pitch, pushed on note-on and shifted on note-off, so overlapping notes each get their own
release. Checked against a stub — playing the same pitch twice and releasing twice now
produces two note-offs, and on the drum mapper the two different mapped notes (open hat
and pedal hat) are each released correctly.

## 5. Objects wired to nothing — FIXED, except the keepalive

Harmless as they stand, but each is an intention that was never finished:

| Device | Object | Note |
|---|---|---|
| Gamepad v80 | `s toTrackMenu` ×2, `r toTrackMenu` | a whole send/receive triple, no cords on any of the three |
| Gamepad v80 | `metro 600000` + `rumble 0.01 0.01 50` | **NOT DONE** — see below |
| Gamepad v80 | third `live.thisdevice`, a stray `0` message | leftovers |
| Kit Selector V4.3 | `loadbang` | dead; the device initialises from `live.thisdevice` instead |
| Dummy Tempo Automator | `live.thisdevice` | dead; that device initialises from `loadbang` instead — the two devices did it opposite ways round |

All removed except the keepalive. **That one was left in place on purpose**: nothing in
the patcher accepts a `rumble` message — `hi` is HID *input* only — so finishing it needs
an object that is not there, which is a design decision rather than a repair. The two
boxes stay as the record of the intention.

## 6. Gamepad scans the whole track list twice on every load — FIXED

Two separate `live.thisdevice` objects fire at load: one sends `init`, the other sends
`refresh` 500 ms later. In `slot-fire.js` both run `scan_tracks(); update_menu()` — the
same work, and `scan_tracks` builds a `LiveAPI` object per track.

**Done** — the immediate path is gone, the delayed one kept. It is the safer of the two:
`init()`'s own comment says it runs "when the API is ready", and the 500 ms delay is what
actually guarantees that. The `↻` button still forces a rescan by hand.

## 7. Transpose Q does a lot of work at the worst moment — FIXED

`applyTranspose` runs on the downbeat and walks **every track, every device, and every
parameter** until it finds one named `Pitch`, building a fresh `LiveAPI` object for each.
On this set that is dozens of objects at the exact instant the bar turns over. It works,
but it is the one place in the rig where a hitch would be audible.

**Done** — the lookup now happens once and is cached as a list of parameter paths; the
downbeat only writes to them. The cache rebuilds itself if the track count changes, and a
`rescan` message clears it by hand after moving devices about.

This also disposed of the substring problem: the group tracks *6 BASS*, *9 PADS* and
*15 LEADS* still match by name, but they carry no `[PITCH]` device, so they never make it
into the cache and are not walked again.

## 8. Small things

- **NOT DONE** — `" Alberton Drum Mapper.amxd"` starts with a **space**. Renaming it
  would break the set: `Alberton Multiverse.als` stores that exact path for all four
  copies of the device, and Live would fail to find them. Rename the file and fix the set
  in one move, with Live closed, or leave it.
- **FIXED** — **Dummy Tempo Automator**: turning *Active* on did not push the dial's
  current value, so nothing happened until you next moved the dial. It now routes the
  toggle through `t i i` (gate first, then the trigger) into a `sel 1` and an `f` holding
  the dial value, so switching it on applies the tempo at once.
- **NOT DONE** — **root-level `inlet`/`outlet` pairs** in Dummy Tempo Automator and PC
  Kit Selector Receiver. They should be inert (a device's MIDI goes through
  `midiin`/`midiout`), but that is belief, not something verified in Live, and if it is
  wrong then removing them cuts MIDI passthrough on those tracks. The gain is purely
  cosmetic, so they stay.
- **NOT DONE** — **Gamepad parameter names collide at index 22**: `mu` and `tp1x` both
  use it (`Map_mu_22` / `Map_tp1x_22`, same for `Min_`/`Max_`). Renaming a device
  parameter drops whatever automation and MIDI mapping the set has stored against it, and
  the collision costs nothing unless something parses the number. Left alone.
- **FIXED** — Drum Mapper comment said `SNARE_RANGE` covers "C#1 a E3"; now C#1–E2.
- **FIXED** — `alberton-transpose.js` and `alberton-transpose-backup.js` were
  byte-identical and unused; moved to `_archive/` beside them rather than deleted.
  **NOT DONE**: `Alberton_Gamepad_v7.6.amxd` (4.8 MB) beside v80 and `Kit_Selector_V4.1`
  beside V4.3 are older device versions that other sets may still reference, so moving
  them is your call, not mine.

## 9. Program change on MIDI channel 1 recalls a kit — ADDED 2026-08-04

Not a defect: a feature that was half-built and had no way to fire.

`Alberton_Kit_Selector_V4.3.amxd` already carried the whole recall path —
`midiparse` outlet 3 (program change) into `+ 1` into `prepend recall` into
`pattrstorage alberton_kits`. What it did not have was any MIDI. The chain was fed by a
root-level **`inlet`**, and a Max for Live device gets its MIDI from `midiin`, never from
an inlet. Every other MIDI device in this set uses `midiin`/`midiout`; this one had
neither.

Added: a real `midiin` into the existing `midiparse`, and a channel filter —
`midiparse` outlet 6 (channel) into `== 1` into the control inlet of a `gate`, with
outlet 3 (the program number) into its data inlet. `midiparse` fires its outlets right to
left, so the channel has already set the gate by the time the program number arrives.
Change the `1` in `== 1` for a different channel.

**PC 0 recalls kit 1** — that is what the pre-existing `+ 1` means, and it lines up with
controllers that display programs from 1.

Safe on this track because *MIDI REC* has no instrument, its MIDI output is **None**, and
its input is **All Ins / All Channels** — so nothing downstream depends on MIDI crossing
the device, and the channel byte survives the trip. No `midiout` was added for that
reason.

**One cord was cut to make this clean.** `+ 1` also fed `prepend goto_part`, and
`live_controller.js` has no `goto_part` function and no `anything()` catch-all — so every
program change would have posted an error to the Max window. Before this change no
program change ever arrived, so it never showed. The `prepend goto_part` box is still
there, now unfed. The set has scenes named *PART 0* to *PART 22*, so what it was meant to
do is guessable, but guessing is not repairing: implement `goto_part` in the script and
reconnect the cord if you want it.

Revert just this change with `Alberton_Kit_Selector_V4.3.amxd.pre-pc-2026-08-04`.

## 10. A device with no `midiout` blocks MIDI for everything after it — FIXED

The one that mattered, found by chasing why §9 did not work.

**In Max for Live a MIDI device passes MIDI on only if it has a `midiout` (or `noteout`)
fed from its input. A device with none does not "leave MIDI alone" — it swallows it**,
and every device after it in the chain goes deaf. Nothing warns you.

*Alberton Transpose Q* had no MIDI objects at all: it works from `plugsync~` and the Live
API, and never needed MIDI. It sat first on *MIDI REC*, so the Kit Selector behind it had
never received a single byte. That is why the program-change recall in §9 did nothing —
and, since the same wiring exists in Kit Selector V3 and V4.1, why it has almost certainly
never worked in any version.

Proved rather than assumed: two diagnostic parameters were added to the Kit Selector,
`Last PC In` and `Last Ch In`, fed straight off `midiparse` before any filtering, and read
over the LOM while the keyboard was played. **Both stayed at zero — not even the channel
number moved**, which no amount of program-change filtering could explain. Moving the Kit
Selector to first position made it work at once.

Fixed by making the quiet devices honest rather than by relying on chain order:

| Device | Change |
|---|---|
| Transpose Q | `midiin -> midiout` added; it uses no MIDI but no longer eats it |
| Dummy Tempo Automator | same — same trap, harmless today only because nothing follows it |
| Kit Selector V4.3 | `midiout` added beside the `midiparse` tap |

Order on *MIDI REC* is now free. The diagnostic parameters were left in place: `MIDI Ch`
selects which channel recalls a kit, and the two read-outs are the fastest way to answer
"is this device receiving anything at all?" — from Live's own UI or over the LOM.

Every MIDI device in the rig now passes MIDI through. *VisualBeat* is an audio device
(`plugin~`/`plugout~`) and is not in a MIDI chain.

Revert these three with the `.pre-thru-2026-08-04` and `.pre-diag-2026-08-04` copies.

## 11. What a session of live testing added — 2026-08-04, evening

Everything above was found by reading files. This came from driving the rig with the
audio running while its owner played, and it is a different kind of harvest: two of the
three things that looked like defects were not defects at all.

### The FX macros at extreme values are deliberate. Do not "fix" them.

Half an evening went into chasing why the drums, then the pads, seemed to stop sounding
while their meters still moved. The cause each time was the **LP / HP FILTER** macro of
that group's `[FX] Alberton per Track` rack sitting at an extreme — 125, 127, 14 — which
removes the audible band without removing the signal. It is written by a kit recall, and
**the owner put those values there on purpose**: a song is meant to start with the bass
filtered, and the kit stores that.

So: a group that has gone quiet is far more likely to be a filter doing its job than a
device that has broken. Check the macro before suspecting anything else.

**Test hygiene, learned the hard way: park LP / HP at 64 before measuring anything.** At
either extreme it is indistinguishable from a dead device, and it cost hours here.

### The Step Sequencer already passed control changes — FIXED anyway, for the rest

An earlier claim in this review, that only notes cross the Step Sequencer, was wrong:
`ctlin -> gate -> ctlout` was already there, honouring the thru switch. What genuinely
did not pass was program change, pitch bend and aftertouch.

Added to both Step Sequencers, each mirroring the existing CC chain and gated by the same
`r ---thruSwitch`: `pgmin`, `xbendin` and `touchin`. **`xbendin`/`xbendout`, not
`bendin`/`bendout`** — the plain pair truncates 14-bit pitch bend to 7 and makes it
steppy. There is exactly one precedent for the 14-bit objects in the whole library, and
it is the right one. Channel aftertouch only; polyphonic aftertouch would need
`polyin`/`polyout` as a fourth chain.

### The Kit Selector, and a caution about adding parameters to it

`MIDI Ch` was added (which channel recalls a kit; §9). Two diagnostic read-outs and a
queue-interval control were added during the hunt and then **removed again**, because of
something worth knowing before anyone adds a control to this device:

**`autopattr @greedy 1` binds every named object, so any new named control becomes a
member of every `pattrstorage` slot** — it gets stored in, and recalled with, every kit.
That is right for `MIDI Ch`; it is wrong for a global setting or a temporary read-out. A
Live parameter with no scripting name would sidestep it, but there is not one example of
that in the 91 devices here, so it is unproven — do not reach for it without testing.

### Still unexplained: 800 "parameter is disabled" errors a day

`live_controller.js` logs `Value cannot be set, the parameter is disabled` around 800
times a day, from 03:11 onward — before anything here was touched. Every parameter on the
pad chains, walked to the bottom including inside racks, reports `is_enabled` true, so
whatever it is writing is not one of those. Unresolved, and worth a look: it is a write
that silently does nothing, every time.

### The pad that would not sound

Chased through four rounds of a timing hypothesis — `live_controller.js` spaces program
changes 150 ms apart to stop Arturia plugins misbehaving, and raising it to 800 ms
appeared to fix the pad. **It did not.** Returning to the original 150 ms, which was the
control experiment and the owner's idea, worked equally well: the pads had started
sounding because the PADS group filter had come back to 64 in the meantime. The interval
was never involved and is untouched.

### How this was checked, and what it does not cover

`analyse.py` in this folder reads a device and reports: dangling `send`/`receive`,
objects no patchcord touches, referenced scripts that are neither embedded nor beside the
device, and every declared parameter. Cross-device wiring was checked by pooling all the
sends and receives together — that is how the Kit Selector ↔ Receiver pair was confirmed
correct rather than dangling.

It does **not** understand `.maxpat` abstractions or image dependencies, so its
"embedded but never referenced" line is meaningless for devices that use them. It cannot
see anything that only exists at runtime, and it does not run the JavaScript — findings
1, 4 and 7 come from reading the scripts.

Nothing here was verified inside Live. Every claim about a file is checkable by reading
it; every claim about *sound* is a prediction.

## 12. Master volume on kit recall raised to 0 dB — CHANGED 2026-09-03, on stage

Made by the owner during a live show, with the set playing; recorded here on 2026-09-08.

`live_controller.js`, `resetVolumes()`: every kit recall resets track volumes to
`VOL_DEFAULT` (0.70, which Live shows as −6 dB) with a few named exceptions, and until
this change it reset the **master** to the same −6 dB. It now has its own constant:

    var VOL_MASTER = 0.85;        // 0 dB; VOL_DEFAULT 0.70 = -6 dB
    ...
    masterApi.set("value", VOL_MASTER);

Two lines changed, nothing else. The device was re-embedded the same minute
(`Alberton_Kit_Selector_V4.3.amxd` and `live_controller.js` both 19:55), so the
embedded copy and the source agree. Backups: `*.pre-master0db-2026-09-03` beside
both files (moved to `_archive/backups/` on 2026-09-08).

Why it matters for the rewrite planned in September: the master target is a policy
of this set, not of the device. The general version keeps the per-kit master level as
a stored dial rather than a constant.

**Closed 2026-09-08.** The owner's answer: the general Kit Selector stores the Main level per kit
as a dial, so the constant goes away with V5 and needs no further explanation.
